# Приглашения: ограниченная серверная роль и одноразовая регистрация

Исправление продолжает PackApprove 3.0. Действующие клиенты, 3D, утверждения и production-файлы не переписываются.

## Воспроизведённая причина

На отдельном локальном Supabase/PostgreSQL создан login `packapprove_test_server` с NOINHERIT и правом `SET ROLE packapprove_app`. До исправления администратор получал 200 при создании приглашения, но `/api/invitations/info` возвращал 500. В логе Next.js: `API failure permission denied for schema auth`; прямой SELECT с ограниченного login отдельно возвращал PostgreSQL `42501 permission denied for table invitations`.

Обычные операции используют `asUser()` и `SET LOCAL ROLE`, а старые `invitationInfo`/`acceptInvitation` обращались к `db` напрямую. Добавить общий SELECT или фиктивный admin actor для публичного маршрута было бы небезопасно. Production-логи и production-база не использовались для этого воспроизведения.

## Новый контракт

Администратор создаёт приглашение обычной авторизованной командой. Роль и организация проверяются сервером; менеджер может приглашать только представителей клиентов. Новая ссылка имеет вид `/invite#token=…`: fragment не передаётся HTTP-серверу или в Referer. Старые ссылки `?token=…` поддерживаются, но браузер сразу удаляет capability из адресной строки. Старые query-ссылки могли попасть в upstream access logs ещё до загрузки страницы — настройки логов хостинга надо проверять отдельно.

Браузер отправляет токен в теле POST `/api/invitations/info`; старый GET остаётся совместимым. Сервер вычисляет SHA-256 и выполняет только три узкие SQL-функции:

| Функция | Назначение |
|---|---|
| `invitation_lookup(hash, lock)` | Проверяет токен, срок, одноразовость, активность/полномочия пригласившего и тип организации. Возвращает только email, роль и имя организации. При регистрации держит row lock. |
| `invitation_finish(hash, auth_user_id, name)` | Повторяет проверки после Auth API; требует подтверждённый Auth UUID с тем же email; создаёт профиль и членство, фиксирует `accepted_at`/`accepted_user_id` и аудит одной транзакцией. Роль и организация из клиентского payload не принимаются. |
| `invitation_registration_state(hash, auth_user_id)` | Проверяет исход неоднозначного COMMIT перед компенсацией Auth. Возвращает accepted/pending/unknown, без пользовательских данных. |

Все функции — `SECURITY DEFINER`, `search_path=pg_catalog`, таблицы полностью квалифицированы. Владелец — доверенный migration owner, не браузерный пользователь. EXECUTE отозван у PUBLIC, anon, authenticated и выдан только `packapprove_app`. Новых table grants и исключений из RLS нет. Нельзя превратить произвольный Auth UUID в администратора: профиль берётся только из действительного приглашения с совпадающим подтверждённым email.

`/api/invitations/accept` создаёт Auth identity, затем профиль/членство через `invitation_finish`; row lock предотвращает гонку двойного клика. Истёкший/заменённый/использованный токен отклоняется до создания пользователя. Существующий email не переписывается: пароль, роль и членства сохраняются; пользователь получает объяснение и ссылку на вход.

## Сбои и ограничения

Auth и PostgreSQL не являются распределённой транзакцией. При известном rollback созданный этим запросом Auth user удаляется, приглашение остаётся доступным. Если COMMIT подтверждён, ошибка автоматического входа сохраняет аккаунт и предлагает войти вручную. Если состояние БД неизвестно, Auth user намеренно сохраняется; удаление потенциально действующего аккаунта не выполняется.

В редком случае timeout Auth create без возвращённого UUID или недоступности компенсации может потребоваться проверка администратором изолированного/боевого Supabase. Перед удалением orphan identity необходимо убедиться, что профиль и принятое приглашение отсутствуют. Автоматически удалять существующий аккаунт или повышать ему роль нельзя.

Публичные попытки ограничены 30 запросами в минуту на IP/endpoint в пределах инстанса; распределённый rate limit при масштабировании требует отдельного edge/Redis слоя. SQL lock timeout — 8 секунд, idle transaction timeout — 30 секунд. Ошибки 400/403/404/409/410/503 объясняют действие пользователю. Логи содержат только код ошибки и, при необходимости проверки компенсации, новый Auth UUID. Токены, пароли, SQL-параметры и provider messages не логируются. Dev-логирование invite URL отключено; `/invite` имеет no-referrer/no-store.

## Применение без ручного набора SQL

1. Backup и отдельный staging Supabase. Использовать существующие серверные env; не добавлять service-role key в NEXT_PUBLIC_. Не направлять изменяющие тесты на production.
2. С подключением **migration owner** выполнить `npm ci`, `npm run db:plan`. Проверить новую `202610250003_invitation_capabilities.sql`; старые миграции не менялись.
3. Выполнить `npm run db:setup` на staging. Приложение продолжает использовать ограниченный login с правом SET ROLE packapprove_app, migration owner в runtime не нужен.
4. Выполнить read-only проверку [invitation_capabilities.sql](../supabase/checks/invitation_capabilities.sql). Ожидаются 3 SECURITY DEFINER-функции с фиксированным search_path, server_can_execute=true, anon/browser_can_execute=false и RLS=true на всех трёх таблицах.
5. Зарегистрировать дизайнера/допечатника по настоящим ссылкам, войти снова, назначить их на проект. Проверить replay, неверный и истёкший токен, существующий email и клиентскую изоляцию.
6. После review и отдельного разрешения повторить additive migration на production **перед** выкладкой нового API. В этой задаче production migration и изменения секретов не выполнялись.

Для отдельного локального стенда автоматическая проверка всей цепочки миграций: `npm run db:test-migrations`. Она создаёт собственную scratch DB, импортирует только auth/storage schema, применяет 4 миграции, проверяет RLS/ACL/search_path и удаляет только созданную ей DB. Production endpoints запрещены.

## Безопасный откат

Аварийный [rollback-файл](../supabase/rollback/202610250003_invitation_capabilities.sql) только отзывает EXECUTE у серверной роли. Регистрация временно блокируется понятной ошибкой; уже принятые приглашения, Auth accounts, профили и членства остаются. Данные и колонка `accepted_user_id` не удаляются. Для восстановления после проверенного исправления повторно выдать EXECUTE на эти три функции из migration owner.

Откат одного интерфейса на предыдущий Vercel deployment не исправляет старый прямой SELECT под ограниченной ролью. Поэтому безопаснее оставить additive schema и выполнить fix-forward API. Автоматического destructive down migration нет.

### Воспроизводимый production-runtime тест

После локального `npm run build` в отдельном терминале: `npm run test:serve-restricted -- --port 3006`. Команда создаёт временный NOINHERIT login, проверяет отказ прямого SELECT и запускает production Next.js с этим login. Секрет соединения не печатается. По Ctrl+C останавливается только созданный сервер и удаляется только созданная тестовая роль.

Затем в другом терминале cloud workspace:

```sh
INVITATION_TEST_ORIGIN=http://127.0.0.1:3006 PLAYWRIGHT_HTML_OUTPUT_DIR=.data/restricted-report npm run test:e2e -- tests/e2e/invitations-wizard.spec.ts --project=desktop --output=.data/restricted-results
```

Сценарий использует реальные fragment-ссылки для дизайнера и legacy query-ссылку для допечатника, повторный вход, создание клиента/проекта, назначение сотрудников и проверку одноразовости. URL очищается до показа формы; новые API-запросы токен в URL не включают. Запуски E2E следует выполнять последовательно, чтобы процессы не очищали общую папку трассировок друг друга.
