# PackApprove 2 — Packaging Operations Studio

Эта ветка обновляет существующий Next.js/Supabase backend, не заменяя его демонстрационной реализацией. Бумажная палитра, редакционная типографика и полиграфические метки — самостоятельная концепция: доступ к официальному брендбуку QAZALPACK не подтверждён. Все показатели берутся из API; ложная пометка LIVE удалена.

## Изменения

- Отдельные представления каталога, назначенных задач, технической очереди, клиентских раундов, исправлений и допуска к выпуску. Каталог поддерживает поиск, фильтры, сортировку и два вида. Превью отображают действительные файлы.
- Ссылки `?view=`, `?project=` и `?artwork=` сохраняют раздел при reload и поддерживают browser Back/Forward.
- Студия PDF сохраняет версии, координатные обсуждения и сравнение; индикатор этапов показывает блокировки следующего шага.
- Пошаговая настройка администратора создаёт производителя и базовый checklist, клиента и безопасные приглашения. Вложенная подготовка в форме проекта сохраняет введённые поля. Неактивные сотрудники не назначаются.
- Управление людьми показывает членство, роли, активность и приглашения. Обновление непринятого приглашения немедленно инвалидирует предыдущую ссылку. Интерфейс явно сообщает, что письмо не отправлялось.
- Исправлена потеря сессии после исчезновения access-cookie; refresh-token используется самостоятельно, параллельные запросы используют общую ротацию в процессе, временный сбой провайдера не удаляет cookies.
- Настоящий recovery с Supabase, PKCE/token_hash callback и сменой пароля без изменения профиля/роли. Подробности SMTP и redirect URLs: AUTH-RECOVERY.md.
- Исправлено независимое завершение технической проверки после отправки клиенту/его утверждения. Передача до успешной проверки по-прежнему запрещена.
- Сохранены immutable versions/decisions, RLS, SHA-256, idempotency, блокировка устаревших решений и отзыв комплекта.

## Безопасная публикация

1. Проверить PR и результаты тестов. Сделать backup Supabase по docs/DEPLOYMENT.md.
2. На тестовом Supabase выполнить `npm run db:plan`, затем `npm run db:setup` под migration owner. Никаких очисток или seed на production. Скрипт последовательно применяет только отсутствующие миграции в транзакции с advisory lock.
3. Новая миграция `202610250001_client_peer_names.sql` добавляет ограниченную SELECT-policy для имён коллег клиента и SECURITY DEFINER-helper с фиксированным search_path и ограниченными execute grants. Она не удаляет/не изменяет бизнес-данные. Исходная миграция не редактировалась.
4. После проверки/разрешения применить эту же миграцию на production. Проверить серверный login с правом SET ROLE packapprove_app, а не выдавать BYPASSRLS браузерным ролям.
5. Проверить существующие серверные SUPABASE_URL / SUPABASE_ANON_KEY / SUPABASE_SERVICE_ROLE_KEY / DATABASE_URL. COOKIE_SECURE=true, NEXT_PUBLIC_DEMO_MODE=false, APP_ORIGIN=https://packapprove.vercel.app. Не менять эти значения автоматически; секреты задаются только в настройках Vercel.
6. В Supabase настроить SMTP и recovery redirect/template по AUTH-RECOVERY.md. До проверки доставки писем не считать email recovery production-ready. Одноразовые приглашения уже могут передаваться вручную.
7. Preview должен использовать отдельный Supabase и соответствующий APP_ORIGIN. Не направлять изменяющие данные тесты на production. Конфигурации Vitest/Playwright теперь отказываются запускаться с нелокальными сервисами.
8. После ревью объединить PR вручную; автоматическое слияние или production deployment агентом не выполнялись.

## Границы проверки

Доступ к packapprove.vercel.app, предполагаемому домену брендбука и api.github.com из облачного окружения возвращал 403 на прокси. Production SMTP, Supabase console, Vercel secrets и реальную email-доставку проверить невозможно без соответствующего доступа. Настройки production не изменялись.

Приложение проверяется на локальных PostgreSQL + настоящих Supabase Auth/Storage. Это не нагрузочное тестирование и не независимый penetration test. Ротация сессии между отдельными serverless-инстансами зависит от механизма refresh reuse Supabase; локальная дедупликация действует в одном процессе. Масштабирование snapshot API/streaming uploads, AV/CDR и ERP остаются отдельными задачами.
