# PackApprove 3 — Interactive Can Studio

Это развитие существующего приложения на базе `feat/packapprove-2-studio`. Согласования, RLS, неизменяемые файлы, технические проверки и производственные комплекты сохранены. Источником текстуры служит конкретный preview-файл версии; браузер повторно вычисляет SHA-256 перед растеризацией и отклоняет несовпадение.

## Как попробовать

В рабочем макете выберите «3D-банка». Версия и UUID файла остаются видимыми; комментарии и решения работают в существующей правой панели. Переключатель версии перезагружает именно её файл и её сохранённые параметры. Точные XY-метки по-прежнему ставятся в 2D; 3D-поворот не создаёт ложных пространственных координат комментариев.

Отдельная страница `/can-lab` содержит только оригинальные публичные демонстрационные развёртки вымышленных брендов. Она не читает клиентские проекты и не заменяет backend. Для неё достаточно Node.js и браузера с WebGL2: `npm ci`, `npm run dev`, затем путь `/can-lab` на локальном сервере. На компьютере пользователя Docker и ключи Supabase для этой отдельной демонстрации не нужны. Рабочий кабинет по-прежнему требует настоящий Supabase. Проверка запуска без backend credentials описана в результатах проверки.

Windows: команды выполняются в PowerShell из папки репозитория; Node.js 24. Npm cache теперь использует переносимый игнорируемый путь `.data/npm-cache`, а не Linux `/tmp`. Генерация демонстрационных файлов нужна только при изменении оригиналов и требует Chromium; уже готовые PNG/JPG/PDF входят в Git.

## Форматы — исключительно визуальные приближения

| Код | Номинал, заданный форматом | Приблизительные H × D, мм | Приблизительная высота печати, мм |
|---|---:|---:|---:|
| Standard | 450 мл | 168 × 66 | 136 |
| Sleek | 330 мл | 145 × 58 | 113 |
| Slim | 250 мл | 134 × 53 | 102 |

Это параметрические исследования пропорций, не проверенные заводские шаблоны. Допуски, вылеты, лак, разделение красок, точные границы печати и конструкция крышки не заявляются. Ширина визуальной развёртки рассчитывается как πD; номинальный объём не выводится из размеров и не изменяется при их выборе. В экспериментальном режиме объём отсутствует. Размеры номинального пресета нельзя переопределить через API — нужен явный experimental.

Точные заводские GLB/GLTF и технологические шаблоны не предоставлены. Замена предусмотрена изолированным контрактом `components/can-studio/model.tsx` (spec + raster). Будущая заводская реализация должна нормализовать единицы, выделить отдельную printable-side mesh с UV, оставить крышку/дно без текстуры и пройти калибровку шва. Клиентские загрузки GLB не разрешены; импорт произвольных моделей сейчас не реализован.

## Геометрия и текстура

Three.js + React Three Fiber создают настоящий WebGL2 canvas: профиль корпуса через LatheGeometry, боковая печать отдельным CylinderGeometry, металлические кольца, крышка, pull-tab и основание. OrbitControls поддерживает мышь/палец, полный оборот, колесо/щипок; клавиатура — стрелки, +/− и 0. Кнопки спереди/сзади/сверху/под углом изменяют реальную камеру.

PNG/JPG декодируются в bitmap; PDF.js рендерит выбранную страницу в canvas. Изображение вписывается с сохранением пропорций или обрезается в cover-режиме. X/Y, масштаб и шов действуют только на ограниченную боковую печатную зону. Крышка и основание остаются отдельными металлическими материалами. Прозрачные области PNG оставляют видимым металл; RGB-белый в PDF не интерпретируется как отсутствие печатной краски.

Параметры и PDF-страница могут фиксироваться только с новой версией в immutable `version_visualizations`. Настройки просмотра не изменяют байты файла и не являются инструкцией для печатной машины. Клиент не получает загрузку/редактирование официальных параметров; выбор ракурса или визуального формата не изменяет утверждённый файл. Согласование по-прежнему относится к UUID и SHA-256 сохранённого файла, не к изображению WebGL. Подсветка, PBR и RGB не являются цветопробой.

## Производительность и доступность

- 3D-модуль и сцена загружаются динамически только при открытии 3D. Проверено сетевыми ответами: WebGLRenderer отсутствует в запросах дашборда.
- DPR ограничен 1–1.5; геометрия ограничена 64/96 сегментами, окружение/тень — 128 px, без внешних HDR и CDN.
- Idle-сцена использует demand rendering; непрерывный цикл нужен только для включённого автовращения. Reduced-motion отключает автовращение.
- Растр ограничен длинной стороной 2048 px; заголовки PNG/JPG проверяются до декодирования (максимум 32 MP). PDF ограничивает область canvas и embedded images. SVG/HTML не принимаются.
- Bitmap закрывается, временный PDF document уничтожается; CanvasTexture освобождается при смене и unmount, R3F/Drei освобождают geometry/controls/context. Полный GPU memory benchmark на физических устройствах не проводился.
- При отсутствии/потере WebGL предлагается действительная 2D-развёртка. Ошибка сцены не убирает возможность согласовать сохранённый файл.
- На телефоне модель идёт первой; настройки свёрнуты в details, обсуждение ограничено по высоте. Шрифт Manrope поставляется локально с кириллицей и расширенной кириллицей.

## Приватная загрузка больших файлов

Новый UI не отправляет файлы Base64 в serverless API.

1. Дизайнер вызывает `/api/uploads/prepare` с artwork ID, kind, именем, размером и клиентской SHA-256. Сервер проверяет сессию, роль, проект, размер и лимит частоты; выдаёт capability только для случайного `_quarantine/user/ticket` в private bucket.
2. Браузер делает PUT непосредственно в Storage. Supabase upload capability действует около двух часов, но не даёт чтения или доступа к финальным объектам.
3. `/api/command` получает маленький JSON с uploadId. В транзакции сервер повторно проверяет владельца/макет/kind/срок/status, читает staging bytes, проверяет фактический MIME, размер и SHA-256.
4. Проверенные байты загружаются сервером под новым final UUID, который никогда не выдавался для прямой загрузки. Это предотвращает подмену immutable версии повторным использованием staging token. Ticket становится consumed.
5. Новая версия, файлы и can spec фиксируются одной SQL-транзакцией. Неудача может оставить недоступный orphan final object (Storage не участвует в SQL transaction); текущий код не заявляет distributed transaction. Повтор того же idempotency key не создаёт вторую версию.

Лимит — 25 MiB на файл. Это прямая, но не TUS-resumable загрузка: при обрыве PUT повторяется целиком. Старый Base64-контракт оставлен для небольших совместимых клиентов; command body ограничен 3.8 MB. SHA-256-verified private downloads выдаются ReadableStream без Content-Length, чтобы не формировать большой буферизированный HTTP response. Для проверки Vercel нужен staging deployment; локальный тест >5 MiB не является подтверждением лимитов конкретного production-тарифа.

Функция финализации использует maxDuration=60 и буферизует один проверяемый файл в памяти перед сохранением/отдачей. При большем масштабе нужны worker/queue, TUS и нагрузочные измерения. Локальный Kong получил CORS только для localhost/127.0.0.1:3000; облачный Supabase должен разрешать upload с вашего frontend origin. CSP connect-src добавляет только origin настроенного SUPABASE_URL, а service role остаётся серверным.

## Обслуживание quarantine

`npm run uploads:gc` — dry run по tickets, истёкшим более пяти минут назад. `--apply --confirm-quarantine-only` удаляет только пути точного вида `_quarantine/user_id/ticket_id`; финальные пути исключены. Remote maintenance требует дополнительного `--allow-remote`, не запускается автоматически. Команда сериализуется advisory lock и пишет аудит. Проверен dry run на локальном стенде; автоматический cron на production не создавался.

Отдельный GC final orphan objects требует retention window и сверки Storage с version_files; он намеренно не удаляет реальные файлы автоматически в этой ветке.

## Безопасная публикация

1. Backup и отдельный тестовый Supabase. Сначала `npm ci` (postinstall готовит локальные PDF.js worker/WASM/fonts), затем `npm run db:plan`.
2. После review применить `202610250002_can_studio.sql` через `npm run db:setup` под migration owner на тестовом проекте. Миграция добавляет две RLS-таблицы, immutable trigger, индексы и default типа для новых макетов. Существующие проекты/файлы не переписывает. Старые миграции не изменялись.
3. Проверить pipeline private upload, MIME/hash rejection, immutable metadata и клиентскую изоляцию. После отдельного разрешения повторить additive migration на production до выкладки кода, читающего новую таблицу.
4. Существующие server-only Supabase/DB переменные остаются. Новые обязательные production secrets не добавлены; service-role key никогда не должен быть NEXT_PUBLIC_.
5. Не запускать seed или изменяющие тесты на production. `seed:cans` разрешён только при demo mode и localhost:54321/54322. Он создаёт отдельную организацию/проект и не заменяет старые клиентские проекты. Повторный запуск сохраняет их.
6. Новый `/can-lab` — публичные отдельные демонстрационные файлы. Реальные клиентские файлы остаются в private Storage и не копируются в public.
7. Не сливать ветку автоматически. Реальные Vercel Preview/production и точные заводские чертежи требуют внешнего доступа и проверки.
