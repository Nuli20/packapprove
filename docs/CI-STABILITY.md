# PR #5: воспроизводимость E2E

Изменения относятся к `feat/product-quality-pass`. Production, миграции и бизнес-правила согласования не меняются.

## Что удалось установить

`git diff 8e91b28 a8a685f` содержит только `docs/PR-PRODUCT-QUALITY.md`.
Публичные страницы GitHub показывают ошибку запуска `40391480063` и успешный
запуск `40431878362` с тем же `a8a685f`. Это подтверждает нестабильность результата
без изменения приложения. API GitHub в рабочем окружении отвечает `Forbidden`,
а подробные логи на публичной странице требуют входа. Поэтому конкретная
длительность отдельных запросов исходного неуспешного запуска неизвестна.

### Диалог решения

`Workspace.command()` после успешного `POST /api/command` ожидал ещё и
`GET /api/state`, прежде чем закрыть диалог. Задержка чтения выглядела как
незавершённое сохранение. Старый тест сразу ожидал скрытия диалога, не проверяя
ответ самой команды.

Воспроизведение: настоящий POST сохраняет решение в PostgreSQL и возвращает 200;
Playwright удерживает последующий GET. Исходный интерфейс воспроизводимо не
проходит `toBeHidden()`; ошибка возникает без ошибки API или двойного решения.

Теперь диалог закрывается после подтверждённого 200. Пока обновляется состояние,
есть доступное сообщение об обновлении и блокировка повторных действий. Если
обновление завершилось ошибкой, сохранённое решение не предлагается отправить
снова. Юридически значимые запись решения, версия и SHA-256 по-прежнему читаются
с сервера; локальная отметка не заменяет их. Ошибка самого POST сохраняет диалог,
введённые данные и сообщение об ошибке.

Новые браузерные проверки на desktop и mobile:

- успешный реальный POST и задержанный, затем ошибочный GET;
- ошибка POST 502: сообщение видно, решения в БД нет;
- потеря успешного ответа: повтор с тем же idempotency key, одна запись с верным SHA;
- двойное нажатие при удерживаемом успешном ответе: один POST, одна запись.

### Общий таймаут полного цикла

Полный цикл включает приглашение/регистрацию трёх сотрудников, реальный Supabase
Auth, восстановление access cookie через refresh cookie, две версии PDF,
Storage, внутренние проверки, комментарий, возврат, согласование, отрицательные
попытки передачи, выдачу точных байтов, получение комплекта и смену пароля через
настоящий recovery token. Все этапы последовательны и проверяют реальный API.

Старые неоднократные запросы `/api/state` загружали весь доступный RLS-снимок,
включая данные других тестов. Их стоимость росла с накоплением проектов, файлов
и комментариев. Теперь используются существующие адресные представления
`setup`, `home`, `project`, `artwork`; неизменяемый шаблон чек-листа читается один
раз. Осталось 39 HTTP-запросов, ни один этап бизнес-сценария не удалён.

Контролируемый эксперимент с задержкой **1400 мс на запрос** перед настоящим
локальным API: исходный сценарий прервался на общем лимите 60 с, успев завершить
32 запроса; адресные запросы завершили весь сценарий за **58,7 с**. Для 39
запросов при задержке 2 с только сетевое ожидание составляет 78 с, дополнительно
нужно время Auth/SQL/Storage. Поэтому **только этому сценарию** выделено 120 с;
глобальные 60 с сохранены. Каждый HTTP-запрос ограничен 15 с: зависший endpoint
не будет бесконтрольно занимать весь бюджет.

Это воспроизведение чувствительности к задержкам, а не заявление о точных
задержках GitHub runner. Простой рост таймаута не устранил бы лишние чтения и
накопление данных.

## Независимые данные и очистка

Полный цикл и три сценария `workspace.spec.ts`, а также новые проверки решения
создают организации, проекты, файлы и клиентские аккаунты с уникальным UUID.
Они не добавляют комментарии к общему демомакету и не набирают согласующих из
общей клиентской организации. Два согласующих и наблюдатель принадлежат только
этому тесту. Проверка политики «Все» дополнительно убеждается, что после
первого решения раунд остаётся открытым.

`OwnedFixture` записывает точные UUID организаций, их имена, собственные адреса
приглашений и ключи команд. `finally` удаляет только их записи, Auth-аккаунты и
объекты приватного Storage. Нет удаления по общему префиксу, очистки таблиц или
изменения общих демопроектов. Неизменяемые фикстуры удаляются владельцем БД в
локальной транзакции очистки с `session_replication_role=replica`; это не
используется при выполнении сценариев и не меняет серверные guards или RLS.
Локальные адреса PostgreSQL, Supabase, приложения и demo mode проверяются до
запуска. Очистка против удалённого сервиса запрещена.

При повторении новые тесты также выявили общий IP-бюджет входов 30/мин: множество
независимых браузеров ранее представлялись одним клиентом `local`. Каждый
OwnedFixture использует собственный IPv6-адрес из документационной сети
`2001:db8::/32` в заголовке тестового прокси для API и браузера. Лимиты приложения
и Auth не отключены и не увеличены, ответы 429 не замалчиваются, общие счётчики
не очищаются. Общие сотрудники используются только как явно выбранные
существующие роли; их профили и пароли эти фикстуры не меняют.

## CI и безопасная диагностика

Workflow выполняет **два полных запуска** desktop + mobile на одной изолированной
БД и одном ограниченном runtime-сервере. Между запусками данные не сбрасываются.
Любая ошибка любого запуска сохраняет красный итог; автоматических retries нет.
Два существующих исключения повторной mobile-проверки платформонезависимого
транспорта сохранены без изменений. Новых `skip` или ослабленных проверок нет.

Сервер запускается прямым Node-процессом, чтобы trap завершал именно процесс,
который закрывает Next.js и удаляет временную ограниченную PostgreSQL-роль.
После ожидания готовности есть обязательная финальная проверка `/api/health`.

CI-репортёр публикует только исходный файл/строку, desktop/mobile, результат,
время, класс ошибки и разрешённые названия API-операций с HTTP-статусом/временем.
`e2e-diagnostics` загружается и при ошибке. Не сериализуются сообщения исключений,
URL, cookies, headers, тела запросов/ответов, пароли и одноразовые ссылки.
Граница фильтрации покрыта Vitest. В CI нет трасс с секретами; локально сохранён
`retain-on-failure`. HTML-отчёты, сырые трассы и `.env` не публикуются.

Для повторения после сборки и запуска изолированного restricted-сервера на 3030:

```bash
CI=1 PACKAPPROVE_TEST_ORIGIN=http://127.0.0.1:3030 PACKAPPROVE_E2E_RUN=1 npm run test:e2e
CI=1 PACKAPPROVE_TEST_ORIGIN=http://127.0.0.1:3030 PACKAPPROVE_E2E_RUN=2 npm run test:e2e
```

Для отдельной проверки бюджета полного цикла, в другом терминале:

```bash
PACKAPPROVE_LATENCY_MS=2000 node scripts/e2e-api-latency.mjs
PACKAPPROVE_TEST_ORIGIN=http://127.0.0.1:3045 npx playwright test tests/e2e/full-cycle.spec.ts
```

Этот прокси слушает только loopback и пересылает только `/api/` на фиксированный
локальный порт 3030; содержимое запросов не выводит. Он предназначен для API-теста,
а браузерные проверки CSRF должны запускаться напрямую на 3030.
