# Product quality pass — выпуск и проверка

Основа: `origin/main` **e7cc0978d082d7fa13cec1586d1f76bc7eade974**. Ветка: `feat/product-quality-pass`. Main, production, домен, облачные настройки и данные не изменялись. Soft Industrial Product Studio — самостоятельная визуальная концепция, не официальный брендбук QAZALPACK. Проверки с записью выполняются только на отдельном localhost Supabase.

## Изменения для пользователей

- Светлая компактная навигация по роли, общий набор кнопок, панелей, полей и состояний. Каталог с настоящими приватными превью, карточками/таблицей, поиском, фильтрами, сортировкой и серверными страницами.
- Обзор, персональные задачи, техническая очередь, согласование, исправления, выпуск, отчёты и аудит получают данные своего раздела. Обычный комментарий больше не означает обязательное исправление. Готовая техническая проверка создаёт задачу отправки для менеджера, ожидание клиента не выдаётся за его действие.
- Добавление независимого макета в существующий проект проверяется сервером. Первое вложение и новая версия различаются. Preview и production выбираются явно; загрузка из 3D не назначает производственный файл автоматически.
- Повтор неоднозначно завершившегося запроса использует прежний idempotency key, а текущие права проверяются до возврата сохранённого ответа. Форма сохраняет выбранные файлы при исправимой ошибке.
- Рабочий 3D использует сохранённую версию, формат и параметры. Есть рекомендуемые пропорции, предпросмотр размещения, предупреждения о полосах/обрезке и контрольная развёртка. Клиент не меняет сохранённый формат. Геометрия приблизительная; визуализация RGB не является цветопробой.
- PDF сохраняется между изменениями масштаба. Превью списка ленивые, одновременно рисуются не более двух PDF; документы и WebGL освобождаются при закрытии.

## Перед рассмотрением выпуска

1. Изучить результаты и снимки в [проверке интерфейса](review/product-quality/README.md). CI использует собственный контейнер PostgreSQL/Auth/Storage и не получает production-секретов.
2. Создать **отдельный staging Supabase**, перенести туда обезличенную копию при необходимости. Preview не должен наследовать production backend. Для Vercel Preview требуется явно заданный `PACKAPPROVE_PREVIEW_PROJECT_REF`; URL Supabase и hostname/username подключения PostgreSQL должны относиться к этому проекту. Без этого приватные API отвечают 503; публичная `/can-lab` остаётся доступна. Это ограничение по умолчанию, не доказательство настроенного staging. На внешнем staging этот выпуск пока не проверен.
3. Выполнить read-only `npm run db:doctor` и `npm run db:plan` на **копии** схемы, используя отдельное owner-подключение `MIGRATION_DATABASE_URL` для CLI. Затем `npm run db:doctor -- --runtime` проверяет отдельно `DATABASE_URL`. Не выводить значения переменных в терминал/PR. Runtime — LOGIN NOINHERIT с SET ROLE `packapprove_app`, без SUPERUSER, BYPASSRLS, возможности получить их через SET ROLE и владения БД/таблицами (включая наследуемое). Сам `packapprove_app` — NOLOGIN, без SUPERUSER/BYPASSRLS. Не передавать migration owner в Vercel runtime.
4. Новых SQL-миграций этому выпуску **не требуется**. Четыре существующих файла сохранены. Doctor сравнивает функции (включая `actor_id`, SECURITY DEFINER, search_path и тело), ACL, RLS, триггеры, столбцы, ограничения и индексы с полными версионированными контрактами. Создание сайта не запускает миграции.
5. Если journal отсутствует, `db:setup` отказывается считать схему установленной по одной таблице. Только полностью совпавший префикс допускает осознанное `npm run db:setup -- --repair-registry` на копии. Для удалённой записи дополнительно требуется `--allow-remote`. При расхождении остановиться, сохранить backup и разобрать различия; не повторять CREATE TABLE и не отмечать миграции вручную. `db:plan` не пишет данные. Контракты не регенерируют ради подавления ошибки.
6. На staging проверить Origin основного домена, recovery redirect URLs/SMTP, приватные файлы, все роли и полный цикл. Не включать demo mode на удалённой базе, не запускать seed. После успешной проверки запросить отдельное разрешение на production. Ветка сама не сливается.

## Откат

Вернуть предыдущий проверенный Vercel deployment/commit после отдельного разрешения владельца. Новых состояний и миграций нет, схема и сохранённые решения совместимы. Не удалять версии, объекты Storage, journal и новые записи пользователей. При обнаружении проблемы доступа закрыть приватный backend до восстановления безопасного runtime, а не выдавать ему BYPASSRLS. Восстанавливать backup только по отдельной процедуре с согласованными Auth, PostgreSQL и Storage; [резервное копирование](DEPLOYMENT.md#резервное-копирование).

## Осознанные ограничения

- Черновик без команды не добавлялся: действующая модель требует реальных активных дизайнера и допечатника. В мастере доступны встроенные приглашения и обновление списков с сохранением заказа. Нет фиктивных назначений.
- Совместимый `/api/state` без `view` оставлен для старых API-потребителей; обновлённый кабинет использует только scoped-запросы. Каталог, очереди, комментарии, журнал, приглашения и комплекты имеют серверную пагинацию. Фильтр организаций каталога показывает до 100 клиентов; текстовый поиск работает по всем разрешённым проектам и организациям. В выборе версии показываются 50 последних записей; более старая версия открывается по прямой ссылке/истории. Ответы внутри выбранной ветки обсуждения пока не имеют отдельной пагинации. Пара сравниваемых версий сохраняется в URL; масштаб синхронен в текущем просмотре, после перезагрузки возвращается к исходному значению.
- Клиентский кеш метаданных принадлежит одному кабинету: до 12 разделов, TTL 15 секунд, очистка при logout/login и смене профиля/роли. Это не кеш разрешений: команды, файлы и новые API-запросы всегда проверяются сервером. Изменение доступа в другом устройстве обнаруживается при следующем запросе, а не через realtime подписку.
- Размер файла до 25 МБ; поток идёт напрямую в private Storage по краткоживущему разрешению, сервер повторно проверяет MIME, размер, hash и привязку перед фиксацией. Нет нового Base64-потока для больших PDF.
- Chromium с SwiftShader и эмуляция телефона не равны Safari/iOS, физическому GPU или скорости сети клиента. Регион облачных сервисов и SMTP не менялись; production-производительность и внешняя доставка писем этим локальным прогоном не подтверждены.
