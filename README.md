# PackApprove · QAZALPACK

Рабочий MVP платформы согласования упаковки: Next.js 16.4.3, React 19.3.1, TypeScript, PostgreSQL 17, Supabase Auth / private Storage / RLS, Tailwind CSS 4, React Hook Form + Zod, PDF.js 6, Vitest и Playwright. Точные версии зафиксированы в package.json и package-lock.json.

Главный инвариант: в производство передаётся конкретная активная версия с неизменяемыми файлами, завершённым клиентским раундом и успешной технической проверкой. Комплект содержит точный file UUID и SHA-256. Его нельзя незаметно переключить на другой файл. Даже администратор не может изменить зафиксированное решение через приложение или обычный UPDATE.

## Быстрый локальный запуск

Требования: Linux, Node.js >=22, npm, Docker Engine с Compose v2, curl. На macOS/Windows используйте Linux VM/WSL2. Свободные порты: 3000, 54321, 54322. Первое скачивание образов Supabase занимает несколько минут и несколько GB диска.

```bash
npm ci
npm run local:up
npm run dev
```

`local:up` запускает Docker Compose с зафиксированными официальными образами PostgreSQL, Supabase Auth, Supabase Storage, PostgREST и gateway, применяет миграции и заполняет демонстрационные данные. Ключи локального Supabase записываются в игнорируемый `.env.local` с mode 0600, в вывод не попадают. Повторный запуск сохраняет существующие данные и конфигурацию. Если `.env.local` уже существует, проверьте его привязки — скрипт не перезаписывает пользовательские файлы.

Стандартный адрес приложения в локальной разработке — порт 3000. В этой облачной среде проверка выполняется внутренними запросами и Chromium. Внешняя публикация приложений не выполнялась.

Для остановки только локальных служб этого проекта:

```bash
docker compose --env-file .data/compose.env stop
```

Не используйте db reset / stop --no-backup при наличии важных данных. При возобновлении облачной задачи процессы надо запустить снова; установленный node_modules сам по себе не означает работающий сервер.

## Как пройти полный процесс

1. Менеджер создаёт проект с клиентом, исполнителями и списком независимых макетов. В макете редактирует версионируемое ТЗ.
2. Дизайнер открывает назначенный проект, загружает новую версию: preview и production обязательны, source необязателен. Файлы фиксируются сразу. Нажимает «На внутреннюю проверку».
3. Допечатник заполняет полный чек-лист, выбирает результат. «Готово с ограничениями» не разрешает production.
4. Менеджер отправляет конкретную версию клиенту, назначает согласующих/наблюдателей и срок. Политика MVP — «Все».
5. Клиент открывает «Согласование клиента» в макете, утверждает или запрашивает изменения. Комментарии добавляются нажатием на макет, ответы — в правой панели.
6. При изменениях дизайнер создаёт следующую версию. Старый открытый раунд становится superseded, сервер отклоняет решение из старой вкладки. Старые замечания доступны в версии; можно связать исправление с новой версией. Сравнение рядом имеет общий масштаб и страницу.
7. После всех утверждений и ready технической проверки менеджер выпускает комплект. Производство скачивает через проверяемый endpoint и вводит SHA-256 фактически полученного файла при подтверждении.
8. Менеджер может отозвать комплект с причиной. История сохраняется, новые скачивания блокируются. Для повторного выпуска требуется новая версия и новый полный цикл.

## Проверки

Нужны запущенный локальный Supabase и demo seed. Это реальные интеграционные тесты, они создают тестовые проекты и private файлы. Не направляйте их на production.

```bash
npm run typecheck
npm test
npm run build
npm run dev                # отдельный терминал
npm run test:e2e
npx tsx scripts/clean-test-data.ts  # только localhost:54322, удаляет проекты TEST / E2E
```

Playwright использует `/usr/bin/chromium`; на другой машине установите Chromium и задайте CHROMIUM_PATH. Системный Chromium в этой среде уже установлен. Отчёт: `playwright-report/`; screenshots и traces: `test-results/`. При использовании собственного Playwright browser измените executablePath или установите chromium соответствующей версии.

20 сценариев Vitest проверяют все 13 обязательных инвариантов, дополнительно неизменяемость решений администратора, MIME/size validation, перенос замечаний, optimistic locking, права файлов и одноразовые приглашения. Playwright проверяет вход, dashboard, создание проекта с сохранением после reload, реальный PDF canvas, координатный комментарий, RU/KZ, решение клиента, отсутствие внутренних комментариев и запрет скачивания отозванного комплекта на desktop/mobile.

## Что реализовано

- Реальный Supabase Auth, обновление сессии, HttpOnly/SameSite cookies, роли из БД; изоляция организаций и назначенных внутренних исполнителей.
- Проекты, независимые макеты, версионируемое ТЗ, неизменяемые файлы, последовательные версии, реальные uploads и downloads в private bucket.
- PDF/PNG/JPEG viewer, масштаб, страницы, fullscreen, координатные комментарии и ответы, внутренние ветки, статусы исправлений и ссылка на новую версию; сравнение рядом.
- Версионируемые checklist templates, ручная техническая проверка конкретной версии, all-policy, неизменяемые решения с preview hash и User-Agent, stale-round rejection.
- Выпуск точного production file, checksum validation на каждом скачивании, получение с проверкой checksum, отзыв с блокировкой повторного скачивания, история.
- Уведомления в базе, deadline reminders CLI, audit log, отчёты по завершённым раундам (replaced/cancelled отдельно), версиям, загрузке и просрочкам.
- Административное изменение роли/active с optimistic locking и аудитом, клиентские организации, одноразовые приглашения с безопасным принятием по ссылке, создание новых версий шаблонов.
- Русский и казахский словари основного UI; мобильная навигация и ключевые клиентские операции.

## Ограничения — до промышленного запуска

Это проверяемый MVP, не сертифицированная промышленная система. Реальные ограничения:

- Приглашения новых представителей работают по одноразовой ссылке (7 дней) с установкой пароля и привязкой организации/роли. Менеджер передаёт ссылку вручную; автоматическая email delivery не настроена. Для уже зарегистрированных пользователей membership сейчас provision через Supabase Admin / SQL. Пароли и access tokens не передавайте в комментариях.
- Нет автоматического preflight (CMYK, шрифты, overprint и пр.) — checklist заполняет специалист. Данные чек-листа/ТЗ хранятся в пользовательском языке; казахский перевод всего контента автоматически не выполняется. Pixel diff отложен.
- Открытые замечания переносятся вручную кнопкой «Перенести замечание», с сохранением исходной ветки и авторов; автоматического переноса всех меток нет. Нет отдельной загрузки вложений в ТЗ; source/ref описаны в ТЗ и файлах версии.
- Уведомления доступны внутри приложения, список обновляется при загрузке и действиях. Нет email/push delivery, WebSocket updates и внешнего ERP/типографского оборудования. Запуск deadline job требует cron.
- Администратор приглашает сотрудников и меняет роли/active. Нет полного UI перераспределения существующих memberships и company settings. Редактирование/архивирование проекта и переназначение исполнителей есть; добавление/удаление макетов после создания проекта пока не предоставлено.
- JSON/base64 upload и download буферизуются в памяти; max 25 MiB на файл. MIME по сигнатуре не заменяет антивирус/CDR. Для production нужны quarantine, отдельный worker, streaming, GC orphan objects и load tests.
- RLS SELECT и application permissions проверены тестами; внешнего независимого security review / penetration test не проводилось. Предполагается доверенный серверный runtime и защищённые owner credentials.
- Нет электронной цифровой подписи/юридической квалификации утверждения, MFA UI и самослужебного восстановления пароля. Уже скачанные файлы отозвать с компьютера пользователя нельзя.
- Snapshot API пока без серверной пагинации, таблицы/уведомления ограничены разумным MVP объёмом; отчёты без CSV экспорта. Произвольные проекты за пределами demo могут не иметь публичного названия контрагента для production, но разрешённые файлы и комплект доступны.
